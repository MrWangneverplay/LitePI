### 10.6 ReLU 孪生网核对 + P₂ 替换损失（明文，全测试集）

**结论先说：不需要重训**。`datas/<ds>_hybrid_s11_seed{73..77}_cnn_train.pt` 就是
canonical 结构、两层精确 ReLU、10 epoch、与 s00 完全同配方训练出的孪生网，
其明文精度即 5.1 表的 s=11 列（97.71 / 58.60 / 89.75），seed73–77 齐备。

真正缺的是「同一套孪生权重，把某层换成 P₂ 之后会不会掉点」——
`analysis/eval_twin_substitution.py` 固定 s11 权重、逐层替换激活重跑明文前向：

| 激活组合 | MNIST (n=10000) | CIFAR-10 (n=10000) | UCI-HAR (n=2947) |
|---|---|---|---|
| ReLU / ReLU（孪生基线） | 97.71 ± 0.09 | 58.60 ± 0.46 | 89.75 ± 0.99 |
| ReLU / P₂（只换第二层） | 81.22 ± 6.88 | 48.15 ± 1.16 | 84.74 ± 1.42 |
| P₂ / ReLU（只换第一层） | 51.59 ± 16.25 | 23.42 ± 1.52 | 63.70 ± 9.17 |
| P₂ / P₂（两层全换） | 31.65 ± 9.55 | 14.43 ± 1.12 | 53.59 ± 14.55 |

结果写于 `results/raw_results/E1/<ds>/twin_substitution/seed{73..77}.json` 与 `summary.json`。

**怎么解释（必须写进论文，否则会被误读）**：本项目的 P₂ 是
`A0 + A1·z + A2·z² = 0.0625 + 0.5z + 0.5z²`，只在 `z ∈ [-1, 1]` 量级有效。
ReLU 训练出来的 `conv/fc1` 预激活会远远越出这个区间，所以「直接替换」不是
「P₂ 的近似误差」，而是**适用域失配**：
- 第二层（fc1 输出）尺度较温和 → 掉 7–11 点，seed 间方差大（UCI 有 79.98 与 58.87 之差）；
- 第一层（conv 输出）动态范围大 → 掉 35–46 点，且完全不可用；
- 这也正好说明**为什么 LitePI 要「按调度重训」**（s00 让网络在训练时就把预激活压在
  P₂ 域内，所以 s00 能保持 97.97/60.59/90.34），而不是拿一套 ReLU 权重硬替换。

因此论文里「多项式近似损失」应报**两个数**：孪生网直换 P₂ 的损失（上表，反映适用域），
以及 s00（P₂ 友好训练）与 s11（ReLU 训练）之间的差值（0.26 / 1.99 / 0.59 点，
反映「同一架构换激活 + 重训」的真实代价）。

代进协议的字节数（§9.2 / §10.2）：

| 环节 | 字节 | 链路时间 @实测带宽 |
|---|---|---|
| 一次性下发评估密钥 `S_key` | 184,634,920 B（176.08 MiB） | **≈ 35.6 s** |
| 单次查询上行 `S_up`（L7 密文） | 917,625 B | ≈ 0.19 s |
| 单次查询下行 `S_down`（L2 密文） | 262,265 B | ≈ 0.05 s |
| 单次查询协议往返（`2 + K_h` 次） | — | 20 ms（s00）/ 40 ms（s11） |

结论：在这条真实链路上，**交互延迟与网络传输合计不到服务端前向的 4%**
（MNIST s11：7.13 s 计算 + ≈0.28 s 网络），瓶颈完全在密文计算；
真正贵的网络环节是**一次性密钥下发 35.6 s**，这也正是 §6.4 密钥裁剪叙事要压的对象。

> 口径：本表是**链路层实测 + 协议字节数**的组合换算，**不是**端到端两机协议跑批。
> 端到端两机需要给 canonical 路径补 TCP 通道（现有实现只在 `socketpair` 上跑），
> 属新增工程，本轮未做；论文中该表须标注为「换算值」而非「实测端到端」。


## 十一、2026-10-28 E7 截断消融（随机截断 vs 直接截断，纯本地）

### 11.1 口径

协议 §4.2 / 实验方案 Phase 4：份额域定点乘法（Beaver）产生 2f-bit 定点结果，须截断回
f-bit。两种方案：

- **direct（直接截断）**：`floor(v / 2^f)`，系统性偏下；
- **random（随机截断）**：以 `(v mod 2^f) / 2^f` 概率上取整，无偏。

误差统一以 LSB = 2^-f 为单位（f-bit 定点最小分辨率），`err = truncate(v_2f) − v_2f / 2^f`。
`v_2f = to_fixed(x)·to_fixed(w)` 是 2f-bit 精确定点乘积，等价于 Beaver 乘法重构后的份额和
（`hybrid_mpc.self_test` 已证 `xy_c + xy_s == x_i·y_i`，精确相等）。

- 参数：Profile B，`f = 8`（`params_b.F`），值域 `[-8, 8]`（激活域）。
- 实现：`hybrid_mpc.py` 的 `direct_truncate` / `random_truncate`（纯 Python/numpy 参考实现，
  **未接 CryptGPU/ABY3**）。E7 验证的是「两种截断算子的误差统计特性」这一数学命题，与
  具体 MPC 后端无关，故可独立成立；论文实现表仍须如实标注后端为 Python 参考实现。
- 5 seeds（73–77），纯本地 CPU，不占远程机。

### 11.2 E7a 单次截断统计（n=200,000 样本/seed，mean ± std over 5 seeds，LSB）

| 模式 | bias | var | rms | max_abs |
|---|---|---|---|---|
| direct | **−0.4903 ± 0.0006** | 0.0841 | 0.5697 | ≤ 0.996 |
| random | **+0.0003 ± 0.0007** | 0.1660 | 0.4075 | ≤ 0.995 |

直接截断每次固定向下偏约 0.5 LSB；随机截断无偏，但方差略大（0.166 vs 0.084），
这是「无偏但噪声略高」的经典 trade-off。关键差别在 bias 是**系统性**的，无法靠平均消除。

### 11.3 E7c n 元点积累加（每项乘积截断后累加，4,000 次蒙特卡洛/seed，bias 单位 LSB）

| n | direct bias | random bias |
|---|---:|---:|
| 1 | −0.506 | −0.017 |
| 4 | −1.957 | +0.002 |
| 16 | −7.825 | +0.002 |
| 64 | −31.32 | +0.078 |
| 256 | −125.2 | +0.35 |
| 1024 | −501.5 | +0.73 |
| 4096 | **−2006.1** | **+1.65** |

### 11.4 结论

1. **直接截断的系统性偏差随运量严格线性累积**：每个乘积贡献 ≈ −0.5 LSB 的确定性向下偏，
   点积长度 n=4096 时累计 bias 达 −2006 LSB（≈ −7.8 × 整个 2^8 定点域）。这正是深度网络
   线性层（n = n_k = 256/1200/756 乃至输入槽位 4096）会踩中的量级。
2. **随机截断保持无偏**：所有 n 下 bias ≈ 0；n=4096 时 +1.65 LSB 只是蒙特卡洛噪声，
   比同点 direct 的 −2006 小约 3 个数量级。
3. **RMS 也拉开**：direct 的 rms 被 bias 主导（n=4096 时 rms=2010 ≈ |bias|），random 的 rms
   是纯方差、按 √n 增长（n=4096 时 rms=123 LSB，比 direct 低约 16 倍）。
4. 这定量支撑协议 §4.2「份额域乘法伴随随机截断」的选型：在 LitePI 的定点推理规模上，
   直接截断会引入不可接受的系统性漂移，随机截断以「无偏 + √n 增长的可控方差」换取精度。

## 十二、2026-10-28 E3 RTT 扫描重算（解析模型，非 netem 端到端）

### 12.1 口径与两处修正

模型（协议 §5.3 / §7.1）：


相对 10-10 旧版（已归档 `_archived_mismatch/E3_rtt_scan_seed73_concurrent_20261028_1552/`）
的两处修正：

## 十三、2026-10-28 E9 极端网络鲁棒性（丢包 × jitter，解析模型）

### 13.1 口径

实验方案 Phase 6 的 E9：丢包 {0,1,5}% × jitter ±30 ms。与 E3 同一决策（§12.7）——
参考原型尚未做 r_h=1 合并，真跑 netem 只能测出原型行为，故 E9 也是解析模型，
计算/字节项复用 E3 的实测输入，只新增丢包与抖动两项：

```
R = 2 + K_h                                   (flights，每层 1 个往返)
C = T_client(s) + T_server(s) + bytes(s)/BW    (计算 + 串行化，无网络)
E[T] = C + R·RTT/(1-p)                         (TCP 式可靠传输，每跳期望重传 1/(1-p) 次)
var_flight = (2J)²/12 + RTT²·p/(1-p)²          (抖动均匀分布 + 几何重传方差)
T_p95 = E[T] + 1.645·√(R·var_flight)           (跳间独立，方差随 R 线性累加)
```

### 13.2 每查询的网络项额外时延（与数据集无关，R=4 即 s=11）

以 RTT = 100 ms、10 Mbps 为参照，相对「无丢包无抖动」的增量：

| 条件 | ΔE[T] | Δp95 |
|---|---|---|
| p=0，J=±0 | 0 | 0 |
| p=0，J=±30 ms | 0 | **+57.0 ms** |
| p=1%，J=±30 ms | +4.0 ms | +70.0 ms |
| p=5%，J=±30 ms | **+21.1 ms** | **+117.2 ms** |

端到端看：MNIST s=11 在 p=5% 时的期望时延 7846.6 ms，只比无丢包的 7825.5 ms 高
**0.27%**。原因不是链路好，而是服务端前向（4.1 s / 15.5 s / 12.5 s）把网络项压成了
小量 —— 论文写 E9 时必须同时给出绝对增量（ms），否则读者会以为丢包被"忽略"了。

### 13.3 K_h*（planner 决策）对丢包完全不敏感

约束仍取 `p95(s) ≤ 1.05 × p95(s=00)`，jitter ±30 ms：

| 数据集 | 10 Mbps | 100 Mbps |
|---|---|---|
| MNIST | K_h*=0（全 RTT） | 1（RTT ≤ 20），RTT ≥ 50 降为 0 |
| CIFAR-10 | K_h*=0（全 RTT） | 2（全 RTT） |
| UCI-HAR | K_h*=0（全 RTT） | 2（RTT ≤ 100），RTT = 200 降为 1 |

**关键诚实结论**：p=0 与 p=5% 的 K_h* 完全相同。丢包只把网络项放大 5.3%，
而预算余量相对整机时延，服务端算力远大于网络项，所以**在 0–5% 丢包区间内
planner 的调度决策不变**。所以「E9 实证轮数可控性」这个说法（协议 §9 措辞）在本模型下
只能支撑到「丢包不破坏调度决策」，不能写成「丢包使 K_h* 下降」。

### 13.4 r_h=1 vs 逐元素 OT：鲁棒性上的量化差别（s=11, RTT=100 ms, 10 Mbps）

| 方案 | flights R | ΔE[T] | Δp95（p=0 / 1% / 5%） |
|---|---|---|---|
| **协议 r_h=1** | **4** | 400.0 ms | 57.0 / 70.0 / 117.2 ms |
| 逐元素 27×4（旧模型） | 218 | 21,800 ms | 21,820.7 / 22,107.2 / 23,257.1 ms |

每层合并成一个往返把 flight 数从 218 压到 4：丢包放大随 R **线性**（E[T] 差 54.5×），
抖动引起的 p95 台面随 √R 增长（√(218/4) = 7.4×，单跳抖动合成的 p95 从 34.6 ms
抬到 255.8 ms）。这是 E9 唯一能进论文表的主结果 ——
它证明 r_h=1 不只是省一次 RTT，而是把「链路劣化 × 往返次数」这个乘积项按 50× 量级压掉。

### 13.5 结论

1. 在 5% 丢包 + ±30 ms 抖动下，LitePI 单查询的期望时延只增加 21.1 ms、p95 增加 117.2 ms
   （R=4、RTT=100 ms；全网格最差点 RTT=200 ms 时 42.1 / 207.1 ms），对秒级的服务端前向可忽略。
2. 鲁棒性的来源是 **flight 数上界**（canonical 2 层 R≤4，VGG 5 层 R≤7），不是丢包率本身。
3. 所以 **E9 不能用来支撑「RTT 越大 planner 越少用 hybrid」**；那一条只有 E3 支撑（§12.5）。
   E9 的角色是「轮数可控 ⇒ 劣化不放大」。
4. 同 E3：这是解析模型，丢包/jitter 项是模型项，**不是 netem 实测**；论文不得写成
   "measured over a lossy/jittery link"。

## 十四、2026-10-29 E1 密文一致率补算（复审 N1 口径）

| uci_har | 1.000 | 1.000 | 1.000 | 0.9969 |
| cifar10 | 1.000 | 1.000 | 0.9969 | 0.9969 |

- 一致率区间 **99.69%–100%**（60 组里 57 组为 64/64，3 组为 63/64）。
- 同一批样本上密文精度与明文精度几乎相等（最大差 0.31 点：uci_har s11
  0.8969 vs 0.9000），说明密文计算本身没有引入调度相关的额外精度损失。
- 由此可以明确写：**s00/s01/s10/s11 的精度差异来自 checkpoint 与样本噪声，
  不是「P₂ 近似优于精确 ReLU」**，与 §10.6 的孪生对照结论一致。
