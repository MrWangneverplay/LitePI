## 2. 修改明细

### A. E10b 成员推理 AUC（`leak_quant.py`）
- 原实现用稳定排序给秩、成员排在前面。"仅索引"特征是 one-hot，打分只有 C 个取值；在并列块里成员总是拿到更小的秩，AUC 因此被压到 0.5 以下。
- 用无信号的随机打分复现：旧代码平均 AUC = 0.455，与 PPT 中的 0.451–0.465 吻合；修复后为 0.505。
- 修复：并列取平均秩（`_average_ranks`）；新增 `auc_bootstrap`，输出分层 bootstrap 95% 置信区间、`max(AUC, 1−AUC)`，以及置信区间是否包含 0.5。
- **影响**：E10b 需要重跑。PPT 第 26 页"0.45 < 0.5 是小样本噪声"的说法要改。

### B. 调度混淆（`pi_server.py` / `pi_client.py` / `pi_proto.py`）
旧实现中，网络观察者可以从下面三点中任意一点读出调度 s：

1. dummy 段的帧类型字节是明文的 `\x03`，真实段是 `\x00`；
2. dummy 段只交换一对密文，不产生 SCI 流量，而真实段会在 SCI 端口上收发 OT 消息；
3. ①/M3 保留各调度自己的 level：hybrid 会把 level 重置到链顶，所以字节数随 s 变化。另外，`ct*0` 是全零的透明密文，开 zstd 后几乎压缩到 0 字节。

修复方式：
- dummy 段改为调用完整的 `hybrid_relu_server`（帧类型 0，按本层的 (q,k) 新鲜掩码，真实跑一次 SCI ReLU），服务端丢弃结果后继续走 P₂。客户端在 dummy 段看到的是 z_k + r_k，与真实 hybrid 层看到的完全相同，不增加泄漏。
- 新增 `obfuscation_levels()`：开启混淆时，每条下行密文都先 mod-switch 到全 P₂ 轨迹在同一位置的 level。这个 level 是所有调度在该位置能到达的最低 level、对应最大 scale，因此任何调度的值都放得下。`_shrink` 在混淆模式下不再按 scale 二次裁剪。
- SPEC 新增 `schedule_obfuscated`，客户端按"每个非线性层一段"的顺序映射层号。客户端仍兼容旧服务端的帧类型 3。
- 新增回归测试 `check_wire_canonical.py --obfuscate`：在 4 种调度下比较观察者看到的帧序列（方向、类型、字节数）和 SCI 调用次数。baseline、seeded、modswitch 三个档位全部 PASS，字节差为 0.000%。本机 SEAL 没有编译 zstd，zstd 档位未测。
- **影响**：E10c 必须用 `pi_server --obfuscate-schedule` 实测重跑；旧的解析估算不能再用。混淆的真实代价是每个 P₂ 层也要付一整段 hybrid 的通信、SCI 和再加密。本地 s00 实测下行从 259 KB 增加到 1539 KB。

### C. r_h 合规（`protocol_contract.py` / `check_protocol_compliance.py`）
- `client_cost` 项改为读取 `results/rounds/r_h_*.json`。如果只有主通道计数（`r_h_sci_*`），状态显示为 **PEND**（不算失败，但也不再显示 PASS）；只有存在 `r_h_netem_*`（scope = end-to-end）时才算已测。
- STAT 新增 `protocol_pending` 字段。

### D. netem 反推 r_h（`netem_e2e.py`）
- 一个约 0.9 MB 的密文在拥塞窗口塌缩后，需要好几个 RTT 才能传完（Linux 默认 `tcp_slow_start_after_idle=1`）。用"墙钟对 RTT 的斜率"计算时，这些 RTT 会被记到 hybrid 层头上。
- 修复：用客户端 `mpc_s` 对 RTT 的斜率除以 K_h 得到每层 SCI 轮数，取 **r_h = 1（①/② 往返）+ SCI 轮数**。墙钟斜率保留为交叉校验，两者相差超过 1 时打印警告。`run.json` 记录 `tcp_slow_start_after_idle` 的取值。
- 合成数据验证：真值 r_h = 8；新方法得 8.00，旧方法得 18.0。
- **跑之前**：两台机器都执行 `sysctl -w net.ipv4.tcp_slow_start_after_idle=0`。

### E. 服务端成本（`cost_model.py` / `planner.py` / `gen_e5,e7,e8`）
- 旧模型对所有数据集使用同一组 `t_server_base`，大约 12.5 s，而 MNIST s00 的实测值是 4.7 s。它也只按 K_h 线性增长，区分不了 s01 和 s10。实测 s10 比 s01 贵 27–44%：岔路把 level 重置到链顶后，FC1 要在更长的模数上计算。
- 修复：新增 `t_server_table_ms[dataset][schedule]`（E1 forward_s 均值）。`server_ms(k_h, arch, bits)` 优先查这张表；fast/VGG 没有密文实测，退回池化模型，并在 basis 字段标注为模型值。
- 用新模型重跑 E7 的 client-aware 消融，**rebound 仍为 1.0**：在三个浅网上，两个目标都选 s00。这是网络本身的性质，不是 bug。论文里这一项要么改用深网（需要深网服务端实测），要么如实写"在 K=2 网络上客户端目标与服务端目标一致"。

### F. 深网可执行性（`planner.py` / `gen_e5_data.py`）
- `deep_hybrid.py` 只支持"前一层是 hybrid 的卷积"，P₂→conv 还没有实现。所以对深网来说，conv1–conv3 之后的非线性层必须走 hybrid。
- 新增 `Layer.next_is_conv` 和 `Profile.executable_only`（默认关闭）。E5 同时报告 `adaptive`（协议层面的最优）和 `adaptive_executable`（当前代码能跑的最优）。
- 试跑结果：VGG 上 `00100` 对应 90 ms，可执行最优 `11100` 对应 618 ms（6.9×）；fast 上 `00111` 对应 98 ms，`11100` 对应 127 ms。论文如果用 `00100` 做卖点，必须说明它依赖尚未实现的 P₂→conv 重排。

## 3. 未改、但必须写进论文 / 汇报的问题

- **H. M2 的统计强度**：MNIST s11 每次查询的统计距离是 2^-30，CIFAR 第一层因为 B=128，σ 只有 35。这个强度低于常用的 2^-40，也与协议 §1.2"统计 64–80-bit"的口径不符；Q_max(2^-20) = 1024，只够 ECG"日千次"场景用一天。根源是 CKKS 用 double 解码（53 位尾数），2^42 的上限不是实现缺陷。可行的提升路径：在 litepi_seal 里用 long double 或四精度做解码 FFT，同时用整数路径编码 r，约可多 10 bit；或者降低 F。§6.2/§11 要改成"统计距离 + Q_max"的写法，并给出这个数字。
- **I. 控制消息泄漏调度**：SPEC（`schedule` 字段）和 STAT 都是明文 JSON。调度混淆只有在加密信道（TLS）上、并且控制消息做定长填充时才有意义；STAT 只是测量用的消息，部署时不应发送。§7.2 要补上这条前提。
- E10a 改用 v2 后，复用组残差不会再是 1e-16，而是 float64 在 2^42 量级下的精度，约 1e-7。结论（完全泄露）不变，但 PPT 上的数字要更新。
- 本地 `datas/mask_domains/` 只有 seed73。seed74–77 的 E1 重跑要先在 101 容器上执行 `export_mask_domains.py`，或者对旧文件执行 `mask_session.py --upgrade`。
- `forward_s` 包含服务端等待客户端完成 hybrid 层的时间，每层约 10–20 ms，相对于秒级的前向时间可以忽略，但需要在 basis 里注明（已写入 provenance）。
- `check_ckks_depth.py` 失败属于旧 TenSEAL profile B 的遗留问题，与本轮改动无关。

## 5. 补充（2026-10-29 晚）：E10b 评估设计与 Delphi 摊销口径

### 5.1 E10b 两处偏差（`leak_quant.py`，已修，待 DeepSeek 重跑落盘）
1. **采样混杂**：成员取训练 loader 前 n 条、非成员取测试 loader 前 n 条。UCI 测试集按受试者/动作顺序排列，前 300 条类别分布偏斜，攻击学到的是类别先验差。旧五种子 UCI 仅索引 0.581、全 logits 0.740 都被这一混杂抬高。
   修复：`stratified_pair` 按真标签分层随机抽样，成员/非成员逐类计数相等。
2. **对半切的反向偏差**：只修采样后，UCI 仅索引变为 0.449–0.487（五种子全部 < 0.5）。原因是攻击在同一批固定样本上对半切训练/评估，one-hot 特征下训练半边的成员富余恰是评估半边的亏欠，学到的规律系统性反向。
   修复：训练集与评估集改为两次不重叠的分层抽样；新增 200 次置换检验，报告 null 均值与 p 值。H6 的判据改为"AUC 与 null 无显著差异"。

本机验证（未落盘，5 种子，每组 300 条）：

| 数据集 | 全 logits AUC | 仅索引 AUC | null | 仅索引 p<0.05 的种子 |
|---|---|---|---|---|
| MNIST | 0.490–0.553 | 0.493–0.505 | ≈0.50 | 1/5 |
| CIFAR-10 | 0.674–0.698 | 0.498–0.542 | ≈0.50 | 1/5 |
| UCI-HAR | 0.495–0.574 | 0.499–0.516 | ≈0.50 | 1/5 |

**对论文的影响**：仅索引档在三个数据集上都与 null 一致（15 次检验 3 次 p<0.05，接近多重检验的期望），H6 的"输出最小化"一半成立。但"全 logits 显著泄露"只在 CIFAR（过拟合最大）上稳健；UCI 从 0.740 降到约 0.54，MNIST 约 0.52 —— PPT 第 26 页"UCI 时序数据最易泄露"的结论来自采样混杂，需撤回。

### 5.2 Delphi 摊销口径（`results/E_delphi/DELPHI_BASELINE.md` §6.4，已改）
旧文写"offline 19.3 s 应视为一次性摊销项"是错的：Delphi 的线性层预处理与混淆电路每次推理都要重新生成，只有 Keygen（376.5 ms）可复用。每次查询客户端成本应按 offline + online 计：7 层配置约 20.1 s / 123 MiB，全 ReLU 约 32.6 s / 3.4 GiB。
