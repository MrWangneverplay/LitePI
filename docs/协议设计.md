# 1. 符号与系统模型

## 1.1 符号表

| 符号                 | 含义                                                     |

## 1.2 系统与威胁模型
LitePI 的核心协议是一个三阶段协议：

1. **离线准备阶段 Offline Preparation**
	客户端设备(Client)生成公私钥对和计算密钥，然后将公钥和计算密钥发送给服务器端（Server）。同时客户端还会生成相应的配置文件，服务器端会根据文件构建资源选择器。

2. **在线低交互推理阶段 Online Low-Interaction Inference**
	低交互推理阶段主要是使用HE-only模式，如果数据规模相对较小的话，可以直接使用$x^2$ 激活函数。这个模式可以是用户在频繁交互模式下。
	如果用户不在频繁交互模式下，可以使用HE-MPC模式，因为HE-MPC模式下的准确度是比较高的，可以在用户初次使用系统时使用（推荐）。
	
3. **资源感知自适应选择阶段 Resource-Aware Planning**
	资源感知自适应是在后期如果用户使用的数据规模较大之后，可以使用这个模式进行选择来使用HE-only还是HE-MPC模式。
	

整体流程如下：

```text
Client Device                         Edge/Cloud Server

Offline:
  - Key generation      ----------->   - Receive public/evaluation keys
  - Optional profile    ----------->   - Build resource-aware plan
                                      - Prepare encoded weights
                                      - Prepare rotation/relinearization strategy
                                      - Select nonlinear evaluation mode

Online:
  - Encode input
  - Encrypt input
  - Upload ciphertext   ----------->   - Homomorphic linear evaluation
                                      - Nonlinear evaluation:
                                        Mode 1: HE-only polynomial
                                        Mode 2: HE-MPC hybrid
                                      - Layer scheduling
                                      - Return encrypted/shared result

  - Decrypt result      <-----------   - Send final result

Output:
  - Classification result

```

![[架构图.png]]

**与双服务器方案的对比（Related Work / Overview 中需各占一段）**：早期部分系统依赖非共谋双服务器假设（如两方秘密分享系），将非线性层拆分给两个独立服务器执行，客户端全程离线。该假设在云服务市场高度集中的现实下难以成立——用户往往只能选择单一服务商。LitePI 的单服务器架构消除了这一信任假设，代价是客户端需参与轻量掩码交互，本文通过 client-light 协议设计将此代价压至最低（hybrid 模式下客户端每层仅做一次解密与一次加法）。这一"信任假设弱化 vs 客户端开销"的权衡本身即是叙事亮点。

- **两方、单服务器、半诚实**：双方忠实执行协议但尝试从接收信息推断额外隐私；恶意模型列为论文扩展讨论，不进第一版实现；
- **保护目标**：C 的输入 x 与全部中间激活；S 的模型权重（CKKS 密文×明文权重计算模式下，权重对 C 天然保密）；C 仅获得输出 y；
- **多查询**：IoT 周期推理（ECG 贴片分钟级、日千次量级）——安全声明按 Q 次查询扩展（§11），这是对 Delphi 系单查询声明的补漏（实验过程结果 4.3）；
- **安全参数**：CKKS poly_modulus_degree=8192（≥128-bit，SEAL estimator 校核【待附录】）；silent OT 计算 128-bit / 统计 64–80-bit，与 CKKS 统一为 128-bit 安全级。

## 1.3 模型族决策（协议主线的关键前提）

| 模型族                       | 激活   | 协议角色                                                                                        | 状态                                                    |
| ------------------------- | ---- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| **ReLU 孪生**（三网络同架构仅换激活重训） | ReLU | **协议主线模型**：HE-only 层 = P₂(x)≈ReLU(x)（逐层近似损失即"多项式代价"）；Hybrid 层 = 精确 MPC ReLU；Adaptive = 逐层调度 | 【待补训：远程服务器，分钟~小时级】                                    |
| Square poly-native（已有）    | x²   | E1 的 Plain-Poly 档；"训练即 HE 友好"路线实证（零近似损失，但函数表达力受限于低阶多项式）；HE-only 消融对照                        | 已就绪（[[HE_Models_Reference]]，97.64% / 62.80% / 89.51%） |

**论证（为什么必须补 ReLU 孪生）**：Square 是深度 1 的多项式，CKKS 可**精确**计算。若协议只在 Square 网上运行，则 HE-only 本身就是零近似误差的精确推理；Hybrid 层把 Square 换成 MPC ReLU 反而引入分布漂移（网络按 x² 的输出尺度校准，下一层权重适配 x² 分布），精度只会更差、还要多付交互轮数。于是"Hybrid 提供精度、HE-only 提供低交互、planner 在两者间调度"的核心叙事失去支点，H1/E1/E5 全部悬空。补 ReLU 孪生后：同一训练模型上，逐层的近似（P₂）与精确（MPC ReLU）才构成可调度的两端——这正是 Delphi 的实验哲学，也是实验方案 3.2.3 原则 4（三档精度报告）的内在要求。

# 2. 协议形式化定义

$$\Pi_{LitePI} = (\textsf{Setup},\ \textsf{EncInput},\ \textsf{LinearEval},\ \textsf{NonlinearEval},\ \textsf{DecOutput})$$

**统一性声明（写作红线）**：HE-only（s 全 0）、Hybrid-all（s 全 1）、Adaptive（planner 输出 s）是**同一协议的三个配置点，不是三个协议**。HE-only 是主干道（2 轮）；Hybrid 是每个非线性层可选的一条岔路（swappable nonlinear primitive）。此定位消除"贡献 = 三个协议拼接"的审稿风险，且与论文草稿 §4 章节结构一一对应。

## 2.1 五算法接口

| 算法            | 执行方                  | 输入            | 输出                           | 阶段       |
| ------------- | -------------------- | ------------- | ---------------------------- | -------- |
| Setup         | C + S                | 安全参数 λ、模型 f_θ | 密钥 (pk, sk, evk)、部署配置、调度向量 s | 离线       |
| EncInput      | C                    | 私有输入 x        | ct_x（im2col 编码后加密）           | 在线轮 1    |
| LinearEval    | S                    | 上一层密文、明文权重    | 本层线性输出密文 ct_{z}              | 在线（S 本地） |
| NonlinearEval | S（s_k=0）或 C+S（s_k=1） | ct_z          | 激活后密文 ct_a                   | 在线（逐层）   |
| DecOutput     | C（档位 A）或 C+S（档位 B）   | ct_y          | logits y 或类别索引               | 在线末轮     |

## 2.2 消息总表

| 编号 | 方向 | 时机 | 载荷 | 大小（§6） |
|---|---|---|---|---|
| M0 | C→S | Setup（离线一次） | pk + evk（relin + 全部所需 rotation keys） | 一次性；E4 实测 |
| M1 | C→S | 在线第 1 轮 | ct_x（客户端 im2col 编码后加密） | ≈336 KB（fresh，L7） |
| ①_k | S→C | hybrid 层 k（仅 s_k=1） | ct_{z_k + r_k} | 208–304 KB（随 level，§5.3） |
| ②_k | C→S | hybrid 层 k 同轮返回 | OT/VOLE 响应 + Enc_pk(c_c) | O(n_k·b) + ≈336 KB |
| M3 | S→C | 在线末轮 | ct_y（或档位 B 的 argmax 交互消息） | 128–336 KB（随 level） |

s 全 0 时在线仅 M1、M3 两条消息、2 轮——"低交互主干道"的字面含义。

## 2.3 协议总伪代码

```text
Protocol Π_LitePI(f_θ, x, s)

Offline (Setup):
  C: (pk, sk, evk) ← KeyGen(1^λ);   send (pk, evk) to S          // M0
  S: 权重量化/编码缓存；packing 与 rotation 规划；
     silent OT 种子与 Beaver 三元组预处理
  Planner: (client profile, network profile, 约束) → 调度向量 s   // §7

Online:
  C: x_enc ← im2col_encode(x);   ct_x ← Enc_pk(x_enc)
  C → S: M1 = ct_x
  S: for l = 1..L:
        ct_{z_l} ← LinearEval_l(ct)            // conv2d_im2col / mm
        if 层 l 后接第 k 个非线性:
          ct ← NonlinearEval_k(ct_{z_l}, s_k)  // s_k=0 → §3；s_k=1 → §4
  S → C: M3 = ct_y
  C: y ← Dec_sk(ct_y)                          // 档位 A；档位 B 见 §9
```

# 3. NonlinearEval 原语一：HE-poly（s_k = 0）

## 3.1 数学定义

Square 特例（当前三网络）：

$$ct_a \leftarrow \textsf{Rescale}\big(\textsf{Relin}(ct_z \odot ct_z)\big)$$

- 深度消耗 1/层（一次密文×密文 + 重线性化 + 重缩放）；零通信、零客户端参与。

一般$P_d$（ReLU 孪生网络上近似 ReLU）：

$$P_2(x) = a_0 + a_1x + a_2x^2,\qquad P_3(x) = a_0 + a_1x + a_2x^2 + a_3x^3$$

- P₂ 深度 1；P₃ 深度 2（x³ = (x²)·x）；

|多项式|拟合准则|a₀|a₁|a₂|a₃/a₄|最大误差|
|---|---|---|---|---|---|---|
|**P₂ minimax（推荐主用）**​|最坏误差最小|1/16 = 0.0625|0.5|0.5|—|**1/16 ≈ 0.063**|
|P₂ 最小二乘|均方误差最小|3/32 ≈ 0.0938|0.5|15/32 ≈ 0.4688|—|≈ 0.094|
|P₄ 最小二乘（升级选项）|均方误差最小|15/256 ≈ 0.0586|0.5|105/128 ≈ 0.8203|a₄ = −105/256 ≈ −0.4102|≈ 0.059|
- 系数在激活值域 [−B, B] 上最小二乘拟合；poly-friendly 训练（激活范围正则）见实验方案 3.2.3 原则 3 [[实验方案设计#3.2.3 设计原则]]与实验手稿 7.2.6。
![[Pasted image 20260907104123.png]]

## 3.2 适用与代价

- **适用**：高 RTT / 低带宽 <font color="#ff0000">/ 极弱客户端</font>（任何 s_k=0 的层）；全部 s=0 即纯 HE 推理；
- **精度代价**：逐层 ΔAcc_poly，由 E1 layer_sensitivity 量化【待补】；
- **注意**：在 Square 训练网络上此原语**精确**（零近似损失）——poly-native 对照路线的意义正在于此（§1.3）。

# 4. NonlinearEval 原语二：Hybrid-ReLU（s_k = 1）

## 4.1 五步消息流（精确数学）

设进入第 k 个非线性层的密文为 ct_z = Enc_pk(z)，处于 level L（轨迹见 §5.3）。

| 步 | 方 | 操作与数学 | 消息 |
|---|---|---|---|
| 1 | S | 采样 r_k^{(q)} ← CSPRNG（§8，满足 M1）；计算 ct_{z+r} = ct_z + Enc_pk(r)（密文+密文加法，**不消耗深度**） | ①_k: S→C |
| 2 | C | 解密：s_c = Dec_sk(ct_{z+r}) = z + r。**解密即份额**：z = s_c + (−r)，加性共享 [z] = (s_c, s_s = −r) 天然成立 | — |
| 3 | 双方 | MPC ReLU：输入 [z]，输出 [σ(z)] = (c_c, c_s)，σ = ReLU。实现：加性秘密共享 + silent OT/VOLE（CrypTFlow2/Cheetah 路线），r_h = 1，在线通信 O(n_k·b) | ②_k 的一部分 |
| 4 | C | 再加密：ct_{c_c} = Enc_pk(c_c)（**客户端在线唯一额外加密**） | ②_k 的其余部分（与 OT 响应**同轮合并发送**） |
| 5 | S | 恢复密文：ct_{σ(z)} = ct_{c_c} + c_s（密文 + 明文份额，不消耗深度） | — |

在线轮数：每 hybrid 层恰 **1 个往返**（r_h=1）——① 与 ② 构成一轮，OT 响应与再加密合并发送，不允许拆成两轮。

## 4.2 关键性质

**性质 1（解密即份额）**：客户端解密 ct_{z+r} 得到的明文本身就是合法加性份额——无需"解密→本地重编码→再加密回份额"的二次转换。对比朴素双向转换（share-to-HE 与 HE-to-share 各走完整流程），本设计省去一次客户端加密与一次交互往返。这是转换层相对 Delphi/GAZELLE 实现细节的非平凡点。

**性质 2（level 重置）**：步骤 4 的再加密产生 **fresh 密文**（回到模数链顶端 L7，166 bit）。因此：
- 乘法深度预算按 hybrid 层**分段重置**：每个 hybrid 层之后的线性/多项式层重新获得完整深度预算；
- 推论：更深的网络可通过"每隔若干层插入一个 hybrid 层"延伸可算深度（CrypTFlow2 同款性质）；
- 这构成 planner 的 **p↔s 耦合维度**（实验过程结果 8.3.1 论证一）：调度 s 改变可行密码参数 p 的下界——纯 HE 路线要求 depth ≥ 模型乘法深度，混合路线可用更小参数。

**实现注意事项**：
- **scale 对齐**：fresh 密文 scale = 2^21，而岔路前的密文处于多次 rescale 后的 scale；后续 mm 的明文矩阵必须按密文当前 scale 编码（服务端编码时对齐，需单元测试覆盖【待测】）；
- 步骤 1 中 Enc_pk(r) 由**服务端**加密（S 持 pk），r 不经信道传输——C 仅通过密文获得 z+r；
- 接口上 σ 可替换为 Sign/比较类非线性（协议不变），第一版只实现 ReLU；
- 定点截断：份额域上的乘法（Beaver）伴随随机截断/随机舍入，误差分析对接 E7 消融（w/o 随机截断）。

## 4.3 为什么 Hybrid 是 ReLU 而不是 Square（论证闭环）

Square 已可被 HE 精确计算（§3），对其再走 MPC 毫无收益。Hybrid 的存在意义 = 精确计算 **HE 算不起/算不了** 的非线性（ReLU 及比较类）。这是 §1.3 模型族决策的推理链另一半：ReLU 孪生提供"值得精确计算的目标"，Hybrid 原语提供"精确计算的手段"，二者互为存在理由。

# 6. 消息格式与字节预算

## 6.1 CKKS 密文尺寸公式与 level 表

N = 8192；数据链 [40, 21×6]（coeff_mod_bit_sizes 末位 40-bit 为 key-switching 专用素数，不承载数据，见 [[HE_Models_Reference]] §2.1）：

$$\text{size}(ct) \approx 2 \cdot N \cdot \lceil \log_2 q_L / 8 \rceil \ \text{字节}\quad(\text{重线性化后 } 2 \text{ 个多项式})$$

| level（剩余素数） | 模数位数 | 每密文字节 | 近似 |
|---|---|---|---|
| L7 fresh（7 素数） | 166 | 344,064 | 336 KB |
| L6 | 145 | 311,296 | 304 KB |
| L5 | 124 | 262,144 | 256 KB |
| L4 | 103 | 212,992 | 208 KB |
| L3 | 82 | 180,224 | 176 KB |
| L2 | 61 | 131,072 | 128 KB |

## 6.4 密钥量（S_key）

- pk ≈ 0.4 MB（2 多项式 × 206 bit）【待实测】；relin key【待实测】；
- rotation keys：索引集 R = R_conv ∪ R_mm。R_conv 由核尺寸/stride/输入行宽决定的窗口位移集组成（O(核面积+行宽) 量级）；R_mm 为对角线法位移集（**输入维度量级**：MNIST FC1 为 256、CIFAR 1200、HAR 756）。全集 evk 可达 MB–百 MB 量级；

# 7. 调度与轮数

## 7.1 调度向量实例化（K=2）

| s | K_h | R_online（r_h=1） | 在线消息数 | 调度泄漏 |
|---|---|---|---|---|
| 00 | 0 | 2 | 2 | 0 bit |
| 01 | 1 | 3 | 4 | 1 bit |
| 10 | 1 | 3 | 4 | 1 bit |
| 11 | 2 | 4 | 6 | 0 bit（相对 K_h=2 无额外不确定性） |

一般地 R_online = 2 + K_h·r_h；调度向量的信息泄漏上界 log₂ C(K, K_h) bit——K=2、K_h=1 时恰 1 bit（服务端从交互发生在哪一层直接看出，无法隐藏，除非混淆）。

## 7.2 dummy-round 混淆（可配置安全档位）

- 开启后：全部 K 个非线性层走交互外观（非 hybrid 层收发 dummy 密文对），调度泄漏 → 0；
- 代价：额外 (K − K_h) 轮 + 每轮 ≈2 ct 传输；
- E10c 量化该档位的开销曲线（泄漏→0 的代价）。

## 7.3 Planner 接口（引用，不重复设计）

输入（模型, client profile, network profile, Acc_min, 预算约束）→ 输出（s, p, packing plan）；三版本搜索策略（rule / greedy / constrained）与三条非平凡性论证见实验过程结果 §8。

# 8. 多查询掩码管理（M1–M3 的协议落地）

| 规则 | 内容 | 协议落地 |
|---|---|---|
| M1 一次性 | 每个 hybrid 层每次查询掩码独立均匀采样，禁止复用 | r_k^{(q)} = PRG(seed_session, q ∥ k)：会话级 CSPRNG 种子 + 计数器模式派生，客户端零额外存储；单元测试断言掩码集合无重复 |
| M2 域对齐 | 掩码采样域覆盖激活分布域 | 每 hybrid 层维护激活值域统计（训练时离线统计 z_k 分布），掩码在该域上均匀采样；E10a 前置检查 |
| M3 重同步 | 随机带失步立即终止并重新密钥化 | 协议状态机：会话计数器 q 不连续/校验失败 → 中止会话 → 重新 Setup |

掩码宽度 = 非线性层维度（§5.2）：MNIST 256/64、CIFAR-10 1200/128、UCI HAR 756/128；每次采样 n_k 个 b-bit 值。E10a 的对照组（故意复用 r）把 M1 从"我们遵守"升级为"不遵守会死"。

# 9. 输出处理（两档 + 一个扩展）

| 档位 | 方案 | 客户端所得 | 额外轮数 | 泄漏 |
|---|---|---|---|---|
| **A（缺省）** | 解密 ct_y 得全 logits，本地 argmax | C 维 logits + 类别 | 0 | 客户端获模型输出几何（含置信度）——E10b 的 MIA 攻击面较大 |
| **B（输出最小化）** | MPC argmax：S 提供 garble/OT 化的 argmax 小电路（C=10/6），客户端求值后仅得 ⌈log₂C⌉ bit 索引 | 类别索引（4/3 bit） | +1 | 输出侧泄漏压缩到索引 |
| C（扩展，**不承诺**） | 密文域近似 argmax（Cheon et al. 比较法） | 索引 | 0 | 同 B |

- 档位 C 的硬约束：模型已用深度 5/预算 6，argmax 需 C−1 次比较的多项式近似，深度不可行；需升级参数（更大 poly degree——planner 的 p 维度）或减层数，列入 Discussion 扩展，不进主实验；
- 档位 B 实现注记：argmax 电路 ≈ O(C·b) 门、garbled tables KB 级，客户端求值开销远小于一个 hybrid 层的岔路开销；+1 轮由 planner 权衡（与 s 联动的又一个输出档位维度）；
- E10b 在档位 A vs B 间量化 MIA AUC 差（对应 H6）。

| 职责 | 客户端 C | 服务端 S |
|---|---|---|

**客户端在线加密/解密计数（client-centric 叙事的硬数字）**：
- s 全 0：**1 enc + 1 dec**；

# 12. 客户端成本对照（非平凡性素材，对 Delphi/GAZELLE/Cheetah）

| 维度（每查询） | LitePI s=00 | LitePI 每条 hybrid 岔路 | Delphi（GC 路线，每 ReLU 层） | GAZELLE/Cheetah |
|---|---|---|---|---|
| 在线轮数 | **2** | +1 | +1（OT 扩展摊入） | +1 |
| 客户端加密次数 | 1 | +1（份额再加密） | +1（份额再加密） | +1 |
| 客户端解密次数 | 1 | +1（解密即份额） | +1（掩码值） | +1 |
| 客户端每层计算 | **0** | 1 dec + OT 响应 + 1 enc | OT 消息 + GC 求值（解析 garbled tables） | OT 消息 + GC/SS 运算 |
| 客户端每层通信 | **0** | ≈2 ct（550–650 KB）+ O(n_k·b) | garbled tables（同量级：n_k·b 门 × ~32 B/门） | 同量级 |
| 全零交互回退 | **有**（s=0 即 2 轮） | — | 有（poly-only） | 无（必交互） |

三个差异化主张（对应实验过程结果 8.3.1 三论证的表格式证据）：
1. **客户端计算维度**：岔路 = 1 enc + 1 dec + OT 响应，无 GC 解析/求值——通信量同量级，计算量差异在弱设备（Pi4/Pi5）上放大（E2 实证）；
2. **轮数可控性**：s=00 时 2 轮；高 RTT 下端到端延迟优势，RTT 扫描中 planner 输出 K_h 单调下降（E3/E9 实证）；
3. **p↔s 耦合**：岔路的 level 重置效应（§4.2 性质 2）使密码参数与调度联合设计成为 Delphi 没有的搜索维度；
加：**多查询安全**（M1–M3 + E10）是对 Delphi 单查询安全声明的补漏，TIFS 差异化点。
